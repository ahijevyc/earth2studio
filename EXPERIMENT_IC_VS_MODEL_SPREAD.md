# AIFS2ENS Spread/Skill Experiment: Model Perturbation vs. IC Perturbation

## Objective

Decompose where AIFS2ENS ensemble spread comes from by comparing two ways of
generating a 50-member ensemble from (nominally) the same starting point:

- **Arm A -- Model perturbation ("standard").** One initial condition (IFS
  deterministic HRES analysis), 50 members generated by AIFS2ENS's own
  internal stochastic noise, varying only the model seed. This is exactly
  what `run_aifs.py` already does.
- **Arm B -- IC perturbation.** 50 initial conditions, one per ECMWF IFS ENS
  perturbed member (`IFS_ENS(member=1..50)`), each run as a single AIFS2ENS
  realization with a **fixed** model seed. Spread here comes from the real
  atmospheric-state uncertainty ECMWF's ensemble already samples, not from
  AIFS2ENS's own noise.

Comparing spread (and RMSE against verifying analyses) between the two arms
tells you whether AIFS2ENS's internal perturbation scheme is capturing a
similar amount/structure of uncertainty as the dynamical IC ensemble does, or
whether one dominates.

**Verification/truth data: `IFS()` deterministic HRES analysis**, valid at
each forecast lead time. ARCO/ERA5 was the initial default choice but isn't
yet available for these dates (ERA5 publishes with a multi-month lag), so
IFS analysis is the truth source for RMSE scoring instead.

## Period

**2026-06-01 00Z through 2026-06-14 00Z**, daily 00Z inits -- 14 initializations.
Chosen deliberately *after* the 2026-05-12 IFS cycle boundary discovered in
`ecmwf-opendata`'s client code (`IFS_50R1_DATE`); dates before that boundary
are missing several fields (wave spectral bands, 10 hPa levels, `sd`) from the
open-data feed entirely. I directly verified 2026-06-01 and 2026-07-01 both
return real (non-zero) values for every field AIFS2ENS needs; I have **not**
yet checked every individual date in 2026-06-01 to 2026-06-14 -- worth a quick
spot check (e.g. 06-07 and 06-14) before committing the full run, since a
single missing date/field combination will currently crash the whole run (see
Caveats).

## Design

| | Arm A: Model perturbation | Arm B: IC perturbation |
|---|---|---|
| Initial condition | `IFS()` deterministic HRES analysis (1 per init date) | `IFS_ENS(member=m)` for m = 1..50 (perturbed members; ECMWF numbers these 1-50, with 0 reserved for the control) |
| Model seed | `14 + member` for member in 0..49 (matches existing `run_aifs.py` convention) | Fixed at `14` for every member (confirmed) |
| Members per init | 50 | 50 |
| Inits | 14 (daily 00Z, 2026-06-01 to 2026-06-14) | 14 (same) |
| Forecast length | `nsteps=20` (120h / 5 days at 6h steps, confirmed) | same |
| Non-IFS/GFS-supported fields | GFS fallback for anything missing from `IFSLexicon` at lexicon-check time | same |

Total model integrations: 14 x 50 x 2 = **1,400**.

### Confirmed decisions

- **Fixed seed (`14`) for every Arm B member.** Isolates IC uncertainty as
  the only spread source in Arm B, rather than conflating it with model
  noise.
- **5-day (120h) forecast length, `nsteps=20`.** Long enough for spread/skill
  divergence between the two arms to become meaningful, at the cost of more
  wall-clock/compute per member and more exposure to the runtime-crash risk
  in Caveat 3 below.
- **`IFS_ENS` member range 1-50** (not 0-50). ECMWF's control (`member=0`) is
  unperturbed by construction, so it's excluded from the "50 IC
  perturbations" set.
- **Verification data: `IFS()` analysis** (see Objective section above), not
  ARCO/ERA5.
- **Wrapper hardening: done.** `run_aifs.py`'s `ERA5WithGFSFallback` now retries
  each variable individually on a primary-source fetch failure before routing
  it to GFS (was previously all-or-nothing per batch) -- see caveat 3 below,
  now resolved.

## Known caveats (everything we've confirmed empirically this session)

1. **Wave-spectral bands are zero-filled in both arms, identically.**
   `h1012, h1214, h1417, h1721, h2125, h2530` and `snowc` are missing from
   *every* open data source we have access to (ARCO, IFS, IFS_ENS, GFS) --
   they get silently zero-filled by GFS's fallback path (`WARNING`-level log,
   no exception). Since this happens identically in both arms, it shouldn't
   bias the *comparison* between arms, but any spread/skill diagnostic
   computed specifically on these fields is measuring zero real variability
   and should be excluded or called out separately.
2. **10 hPa levels and `sd` are real for June 2026 dates**, confirmed for
   2026-06-01 and 2026-07-01 directly against both `IFS` and `IFS_ENS`.
3. **No runtime-failure fallback -- RESOLVED.** The wrapper originally only
   caught lexicon-lookup `KeyError`s before deciding whether to route a
   variable to GFS; a live-fetch failure at runtime raised uncaught and
   killed the whole run. `ERA5WithGFSFallback` now retries a failed batch
   fetch one variable at a time and routes only the variables that actually
   fail to GFS, so a single bad field/date no longer aborts the rest of a
   member's rollout.
4. **New bug found and fixed during this experiment: IFS_ENS wave-sentinel
   leak.** IFS_ENS's GRIB decoding leaks a `9999` missing-data sentinel
   through as real data in wave-stream fields (`cdww`, `cos_mwd`, `sin_mwd`,
   `mwp`, `swh`, and the `h1012..h2530` spectral bands) over land and
   ice-covered ocean. This was the root cause of a smooth, unphysical global
   cooling drift traced through a full Arm B rollout -- feeding AIFS2ENS a
   value ~1000x a field's normal range is a catastrophic out-of-distribution
   input. Fixed in `run_aifs.py` by masking any value >= 9998 in those
   variables to 0 (matching deterministic IFS's own convention for the same
   regions). Confirmed Arm A (built on `IFS()`, which doesn't exhibit this
   leak) never showed the drift, isolating the cause to IFS_ENS's decoding
   rather than AIFS2ENS itself.
5. **ECMWF open-data S3 rate limiting.** We hit `503 Slow Down` errors
   ourselves this session under repeated rapid requests. A 1,400-run
   experiment fetching from the same open-data bucket will need reasonable
   pacing/backoff (the `ecmwf-opendata` client already retries with backoff,
   but sustained high request rates could still be slow or throttled).
6. **`run_aifs.py`'s current append/skip logic is member-and-init aware**
   (skips an init date already present in a member's zarr store), which
   gives natural crash-resume behavior -- worth reusing rather than
   rebuilding for this experiment's driver script.
7. **New bug found and fixed: ensemble spread computed as mean(std) instead
   of sqrt(mean(variance)).** The first-pass spread computation averaged
   per-gridpoint standard deviations (across space, then again across the 14
   inits) before ever taking a square root. Since `sqrt` is concave, this
   systematically *underestimates* spread relative to the correct
   sqrt(mean(variance)) (Jensen's inequality) -- confirmed 15-27% too low,
   worse at longer lead times and for z500/t2m than t850. Fixed in
   `compute_spread_correct.py`, which keeps everything in variance until one
   final `sqrt()` (matching how RMSE itself is computed: average MSE, sqrt
   once) and additionally applies the `(R+1)/R` exchangeability-factor
   correction (Fortin, Abaza, Anctil & Turcotte 2014) on top of the usual
   `ddof=1` Bessel correction, since spread-vs-truth RMSE behaves as if truth
   is one more member exchangeable with the ensemble. **Any spread/skill
   number computed before this fix (anything not going through
   `compute_spread_correct.py`) should be treated as unreliable.**

## Output layout

Two families of zarr stores, following the existing naming convention --
**both fully populated** (50 members x 14 inits each, confirmed via
`run_ic_vs_model_spread.log` / `run_arm_b_only.log`):

```
AIFS2ENS_IFSControl_member_{000..049}.zarr   # Arm A, time dim = 14 daily inits
AIFS2ENS_IFSENS_member_{001..050}.zarr       # Arm B, time dim = 14 daily inits, member index = ENS perturbed member number
```

Consolidated into compact per-arm caches plus a shared truth cache
(`build_arm_a_cache.py`, `build_arm_b_cache.py`, `fetch_ifs_truth.py`):
`arm_a_cache.zarr`, `arm_b_cache.zarr`, `ifs_truth_cache.zarr`.
